# Security

How Wejhaty is protected, what those protections are worth, and where they end.

## What the app is

Wejhaty is a static bundle. It has no server, no database, no accounts, no
API keys, and no analytics. The recommendation engine runs entirely in the
visitor's browser, and the destination data is compiled into the bundle. The
app makes no network requests after the page loads.

That shape decides everything below. There is no server to breach, no
credentials to steal, and no stored personal data to leak. The realistic
threats are the ones that apply to any web page: getting hostile markup to
execute in a visitor's browser, tricking a visitor through a framed copy of
the page, or leaking who visited to a third party.

## Protections

### No third party is contacted

The site previously loaded its typefaces from Google Fonts. Every visitor's
IP address and User-Agent reached a third party before a single word rendered.

Cairo, Inter and Fraunces are now served from the site's own origin
(`app/src/assets/fonts`, generated by `npm run fonts:refresh`). Weights and
`unicode-range` values are copied from Google's own stylesheet, so text
renders exactly as before.

The build enforces this. `vite.config.ts` scans every emitted file and fails
the build if any references an origin other than the site's own. Adding a CDN
script, a tracking pixel or a remote font breaks the build rather than
shipping.

### Content-Security-Policy

Injected into the built `index.html` at build time:

```
default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self'; connect-src 'none'; manifest-src 'self';
base-uri 'none'; form-action 'none'; object-src 'none'; upgrade-insecure-requests
```

`connect-src 'none'` is the important one. Even if an attacker managed to run
code on the page, the policy gives it no channel to send anything out.

`script-src 'self'` permits neither `unsafe-inline` nor `unsafe-eval`, so
injected `<script>` tags and inline event handlers do not run.

`style-src` keeps `'unsafe-inline'`, and that is a deliberate, narrow
exception. React writes the `style` attributes this interface uses for flag
sizing and region gradients. The precise alternative, `style-src 'self'` plus
`style-src-attr 'unsafe-inline'`, is not implemented in Firefox, which would
fall back to the stricter rule and break the layout. The residual risk is
small: the app renders no user-supplied content, so there is no path by which
an attacker's CSS could reach the page.

The policy is applied at build time only, so the development server keeps its
hot reload.

### The SVG allowlist guard

The app writes raw HTML into the DOM in exactly four places: the country flags
and the interface icons, both inline SVG. That is its only injection surface.

`app/src/security/svgGuard.ts` checks every SVG string against an allowlist of
elements and attributes before it reaches the DOM. Anything outside that
vocabulary is rejected outright and the component renders its normal fallback.
The guard never rewrites or repairs markup, so valid artwork passes through
byte-for-byte and the flags render exactly as before.

Rejected: `<script>`, `<style>`, `<foreignObject>`, `<iframe>`, animation
elements, every `on*` handler, `style` attributes, `javascript:` and `data:`
values, references to any other origin, and unquoted attributes.

Two tests keep this honest:

- `svgGuard.test.ts` proves all 30 flags and every icon pass unchanged, in both
  fit modes and after id rewriting, and that 18 attack payloads are rejected.
- `injectionSurface.test.ts` fails if a new `dangerouslySetInnerHTML` appears
  anywhere that does not consult the guard, or if any source file introduces
  `eval`, `new Function`, `document.write`, `fetch`, `XMLHttpRequest` or a
  WebSocket.

### Supply chain

CI installs with `npm ci --ignore-scripts`, so a dependency's install hook
cannot run with write access to the artifact being published. `npm audit`
runs at moderate severity on every change. Neither workflow persists a git
credential into the checkout.

The deploy workflow refuses to publish if the built `index.html` or `404.html`
is missing its policy.

### Privacy

The app stores nothing about the visitor on a server, because there is no
server. Quiz answers live in React state and disappear when the tab closes.
`<meta name="referrer" content="no-referrer">` stops the visited URL from
leaking to any other origin.

## Limits

**GitHub Pages cannot set response headers.** This is the significant one.

A `<meta>` policy cannot express `frame-ancestors`, so on GitHub Pages the
site cannot refuse to be embedded in another page. Clickjacking protection,
`X-Content-Type-Options: nosniff`, `Permissions-Policy` and HSTS all need real
HTTP headers.

The build generates `dist/_headers` with the full set, which Netlify and
Cloudflare Pages apply automatically. Moving the site to either host, or
putting a CDN in front of it, closes this gap with no code change. On GitHub
Pages the file is served but ignored.

**Client-side code is readable.** Minified JavaScript is not secret. Source
maps are disabled so the readable source is not republished alongside the
bundle, but anyone can read what ships. Nothing confidential belongs in this
bundle, and nothing confidential is in it.

**The destination data is demo data.** It is sample content for a prototype,
not current official statistics.

## Running the checks

```
cd app
npm run verify          # lint, tests, build guard, dependency audit
npm run security:check  # the above, plus a real browser: CSP violations,
                        # foreign requests, console errors, rendering
```

`security:check` needs Playwright available on the machine
(`npm i -g playwright`). CI does not use it; the unit tests and the build-time
origin guard cover the same ground without a browser.

## Reporting a problem

Open an issue on the repository. There is no user data at risk, so nothing
here is urgent in the way a breach would be, but a bug in the guard or a gap
in the policy is worth fixing quickly.
